## Port Scan Investigation

## Incident Summary

A simulated network port scan was conducted against the Windows VM from the Kali Linux VM in a controlled home SOC environment.

Nmap was used to generate scanning activity, Wireshark and Windows/Splunk telemetry was used to observe and investigate the resulting network activity.

The purpose of the exercise was to determine whether repeated connection attempts to multiple destination ports could be detected and investigated using Splunk.

## Attack Source

Kali Linux VM

The Kali VM was used as the simulated attacker and generated the Nmap scanning traffic.

Source IP: 192.168.1.34

## Target

Windows VM

The Windows VM was the target of the simulated scan.

Destination IP: 192.168.1.35

## Detection

The activity was detected using Windows Firewall logs ingested into Splunk.

The Splunk detection extracts the source IP, destination IP, source port and destination port from the firewall log and groups network activity into five-minute windows.

The detection identifies cases where a source contacts a high number of unique destination ports within the same time window.

index=main sourcetype=firewall
| rex field=_raw "^\S+\s+\S+\s+(?<action>\S+)\s+(?<protocol>\S+)\s+(?<src_ip>\S+)\s+(?<dst_ip>\S+)\s+(?<src_port>\S+)\s+(?<dst_port>\S+)"
| bin _time span=5m
| stats count dc(dst_port) as unique_ports values(dst_port) as destination_ports by _time src_ip dst_ip
| where unique_ports >= 10
| eval detection="Potential Port Scan"
| eval severity="Medium"
| sort - unique_ports

## Timeline

Attack preparation — Kali Linux was configured as the simulated attacker and the Windows VM as the target.
Scan execution — Nmap was run from Kali against the Windows VM.
Network observation — Wireshark was used to observe the traffic generated by the scan. SYN packets associated with the scanning activity were examined using the filter tcp.flags.syn==1 && tcp.flags.ack==0.
Log collection — Windows firewall and endpoint telemetry were collected by Splunk.
Detection — Splunk was used to identify repeated connection attempts across multiple destination ports.
Investigation — The source and destination IP addresses and destination ports were examined to determine whether the activity was consistent with network scanning.

## Investigation

The first step was to identify the source and destination of the network activity. The source was the Kali Linux VM and the destination was the Windows VM.

The destination ports were then examined to determine whether the source was attempting connections across multiple ports rather than communicating with a single service.

Wireshark provided supporting network evidence by showing repeated SYN packets generated during the Nmap scan.

The Splunk detection grouped the firewall events into five-minute windows and counted the number of unique destination ports contacted by each source and destination pair.

Because the activity was generated intentionally from the Kali VM as part of the lab, the scanning behaviour was expected and could be attributed to the controlled simulation.

## Findings

The investigation confirmed that the Kali Linux VM generated network scanning activity against the Windows VM.

The activity produced observable network traffic in Wireshark and corresponding firewall telemetry that could be searched and aggregated in Splunk.

The activity involved connection attempts across multiple destination ports, matching the behaviour the detection was designed to identify.

No conclusion about a real-world compromise is made because this was a controlled laboratory simulation.

## Conclusion

The port-scan detection successfully demonstrated how network reconnaissance activity can be identified using Windows Firewall telemetry in Splunk.

The investigation also demonstrated the value of correlating SIEM data with packet-level evidence from Wireshark. The combination of Nmap, Wireshark, Windows Firewall logs and Splunk provided visibility into the simulated attack from generation through detection and investigation.

## Recommended Response

In a real SOC environment, an analyst responding to a similar alert would:

Identify and validate the source IP.
Determine whether the source is an authorised vulnerability scanner or security-testing system.
Examine the destination ports and scan frequency.
Review other activity from the same source IP.
Check whether the scanning was followed by connection attempts or exploitation activity.
Review relevant endpoint and authentication logs on the target.
If the activity was unauthorised, escalate the alert for further investigation and consider appropriate containment actions.

For this lab, no remediation was required because the scanning activity was intentionally generated as part of the controlled simulation.
